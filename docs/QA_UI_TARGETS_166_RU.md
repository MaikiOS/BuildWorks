# QA UI-цели .166 — офлайн, 2026-10-12

Подготовлено для полного локального исполнителя. Игра/модель/GPU не запускались,
DLL не устанавливалась; установленная QA остаётся .165. Это предварительная часть
канала, не готовый полный агент и не прохождение S01–S12.

В `response.json` добавлены `uiTargets` и `uiTargetsTruncated`. Одна цель содержит
непрозрачный `id`, тип, название, значение, признаки writable/focused, нормированные
координаты центра (Y снизу) и экранные границы. Видимыми считаются активные,
доступные `Selectable`, в центр которых первым попадает native `EventSystem.RaycastAll`.
Если первое попадание — перекрывающий объект, кнопка под ним не выдаётся.
Это проверка доступности центра, не всей поверхности. Неподвижная неизменённая
цель сохраняет ID между наблюдениями; перемещение, смена названия/значения,
разрешения или UI-системы требует нового ID. Полные значения сравниваются и тогда,
когда в ответе показаны только первые128 символов.

Ограничения: максимум32 цели и12000 байт компактного JSON целей на ответ; усечение явно
отмечается. Сейчас нет страниц/поиска остальных целей, drag, IMGUI или обхода
перекрытий. Отсутствие цели не означает отсутствие функции. Идентичность контрола
и его видимый текст не доказывают ID выбранного чертежа/предмета: соответствующие
снимки состояния ещё нужны перед операциями с данными или ресурсами.

Протокол batch принимает `uiTarget` только в первом из двух шагов:

```json
[
  {"milliseconds":100,"uiTarget":"<32 hex из свежего ответа>","pointer":true,"buttons":1},
  {"milliseconds":300}
]
```

Координаты для такого клика берёт хост из проверенной цели. Смешивать его с
движением, поворотом, колесом, другими кнопками/клавишами или последующим действием
в том же batch нельзя. `stopRevision` обязателен. Перед началом и во время
удержания до отпускания повторно проверяются конкретный живой контроль, экран,
геометрия, текст/значение и первое попадание. Смена после уже выполненного
отпускания допустима: кнопка может штатно закрыть своё окно. Сбой вызывает прежний
Stop с отменой незавершённых UI-жестов; совершённые действия не откатываются.

Ввод текста использует такой же ID и два шага: первый содержит `text` (до256
символов), при необходимости `keys:["Return"]`; второй нейтрален. Обязательны
конкретное выбранное поле, его реальный `isFocused`, доступность и отсутствие
readOnly. Сначала поле надо сфокусировать штатным кликом. Изменение текста и
Submit не подтверждают сохранение файла. Разрешённые поля и значения должен
ограничить исполнитель по задаче; наличие этого API не разрешает модели ввод
произвольных игровых команд.

Прямых вызовов `Button.onClick` нет: используются прежние виртуальные устройства
и native UI input module. Старые ручные batch без `uiTarget` сохранены; локальный
модельный пилот всё ещё не допускает произвольные клики/текст. Новая API сама по
себе не расширяет его `allowed_actions` и не меняет критерии успеха сценариев.

Проверено офлайн: normal/QA .166 без предупреждений;43 проверки протокола,
40 проверок производственного observer/guard на инертных UI-объектах, прежние
проверки publisher и14 text-submit,12 случаев actual Respond; compiled QA
isolation/native input contract, HostContract, localization989, Python
mission4/scenarios3. Независимый correctness PASSED/Ponytail Ship. `verify` отсутствует.
Первый sandbox-прогон publisher упал с `IOException: Не удается удалить заменяемый
файл`, Python journal — с WinError5; повторы CPU вне sandbox прошли. Рабочие файлы
игры не менялись. Inert UI и IL не доказывают настоящий raycast, фокус, нажатие,
производительность или отсутствие лишнего клика в Valheim.

Дальше офлайн: подключить цели к полному исполнителю с разрешёнными полями и
проверяемыми снимками чертежа/объектов/предметов, учётом ресурсов и reload.
`safe_ui_targets` в сборщике сценариев пока не помечается доступной: требуется
установка после разрешения, игровая проверка и модельная интеграция.
