# Оплаченная отмена: границы и план реализации

Подтверждённое поведение: отмена возвращает фактически потраченные предметы с их свойствами выпадением рядом с табличкой. Неоплаченный проект просто исчезает. Старое состояние предметов не восстанавливается, повторной выдачи нет. Рельеф не меняется. Общая будущая табличка/хранилище — отдельная [граница EarthWorks](EARTHWORKS_BOUNDARY_RU.md).

Ниже технический проект, а не готовая функция или утверждённый новый интерфейс. Начальное ограничение: private Local host, тот же оплачивающий игрок, проверенные ванильные конструктивные части. Сеть, содержимое и произвольные `IRemoved` требуют отдельного доказательства.

## Порядок и сохраняемые состояния

1. Заморозить продолжение; дождаться и сверить pending исполнения. Зафиксировать cancel ID, проект/revision, часть/receipt, мир, плательщика и точные PaidRows. Неизвестное состояние останавливает отмену.
2. Проверить живую уникальную собственную часть; сохранить намерение удаления, подавить обычные native drops и удалить. Сохранить мир, проверить отсутствие всех целевых меток одним полным mapped scan. .237 реализует только этот последний read-only примитив.
3. Для каждого возврата сохранить IssueIntent, затем создать ItemDrop у таблички с отдельной ZDO-меткой cancel/row/receipt и закрытым подбором. Метка должна ставиться в раннем spawn-пути, включая исключение после Instantiate; голое окно между spawn и tag недопустимо. Доказать точные native данные предмета и сохранённый единственный drop, затем записать Issued. Это уже выдача, ещё не подбор.
4. После сохранённой выдачи всех строк завершить отмену, убрать табличку/туман; журнал выдачи оставить. Подбор маркированного drop сохраняет CollectIntent и точный inventory-before; помещает исходный предмет в проверенную пустую ячейку без штатного merge, подтверждает сохранённый профиль, затем удаляет drop и подтверждает сохранённое отсутствие. Лишь после этого Collected.

## Сбой и повтор

| Наблюдение после восстановления | Решение |
| --- | --- |
| Часть отсутствовала до контролируемого удаления | Не считать возврат безопасным: обычные drops могли уже выпасть |
| Намерение удаления, но исход неизвестен | Сверка receipt/живого и сохранённого состояния; неопределённость блокирует выдачу |
| IssueIntent, метка drop не найдена | **Не создавать автоматически заново:** отсутствие не доказывает, что предмет никогда не выдавался/не подобран |
| Найден один точный закрытый drop и сохранённая выдача | Продолжить по журналу, без повторного spawn |
| Дубликат, неизвестное слияние, неполные данные | Остановить конкретную строку, сохранить доказательства |
| CollectIntent и точный сохранённый inventory-before/after | Продолжить только однозначную ветвь; частичный результат не угадывать |
| Issued drop исчез без доказательства Collect | Остановить строку, не выдавать повторно |

Native `Inventory.FindFreeStackItem` не учитывает все customData/variant: item customData не подходит как единственная долговечная идентичность возврата. Использовать ZDO-метку и проверенный pickup-путь; до реализации запрета pickup/auto-stack/despawn/cleanup функция не включается. Поведение при отключении мода остаётся отдельным риском.

## Следующие проверяемые срезы

- Сохраняемый cancellation journal и переходы с fault injection.
- Контролируемое удаление/подавление drops и game save/readback.
- Ранний tag+seal spawn, точное чтение ItemDrop.SaveToZDO, Issued/Collected.
- Проверка сбоев между каждым шагом; native прогон отмены/подбора/reload, затем сервер.

До этого оплаченная кнопка отмены остаётся закрытой. Положительное чтение файла, RAM refund-флаг или absence proof не заменяют весь протокол.

## Следующий срез долговечного завершения — проект20.10, ещё не реализован

Отмена не должна ждать, пока игрок подберёт все возвраты. После подтверждённой выдачи всех drops здание/туман/табличка исчезают; подбор и очистка источников продолжаются отдельно. Состояние полного расчёта — следующий этап, оно не задерживает завершение отмены для игрока.

Предложение архитектора: сохранить прежние байты rev1/rev2 и добавить rev3 «оплаченная отмена, возвраты ожидают получения», затем rev4 «все возвраты подтверждены». Это технический Draft формата/API, не готовые revisions. Rev3 привязывается к неизменным данным удаления/выдачи и свежему отсутствию construction-меток. Fingerprint выдачи не включает изменяемые Collections. Receipt/подбор/отсутствие payout drops для rev3 не требуются. Rev4 дополнительно проверяет все ProfileCredited/CleanupSaved, постоянные receipts и общий scan двух групп из .250.

После rev3 табличка не воссоздаётся, но collection/cleanup должны оставаться доступны без OpenBoard. После rev4 журналы доступны только для сверки. Неизвестный исход, rollback, повторившийся источник или потерянная receipt замораживают сверку без новой выдачи/постройки/удаления. Сам metadata-переход не меняет мир и инвентарь. Полный согласованный rollback всех файлов не обнаруживается без внешнего монотонного якоря; такая гарантия не заявляется.

Первоначальное предложение одного rev3, допускаемого лишь после подбора всех drops, **отклонено как не соответствующее порядку действий игрока**. Сначала доказать совместимость старых записей, оба атомарных перехода/replay, продолжение получения без таблички и startup/fault/rollback на host substitutes; затем native. Два старых полностью полученных Wood-долга — частный QA-случай, не основание требовать немедленного подбора в обычной отмене.

## Уточнённая рекомендация21.10 — слой сохранения реализован, игровой переход открыт

Два независимых чтения заменяют предложение rev3/rev4 выше: сохранить существующие rev1 «активен»/rev2 «отменён», а ожидание и завершение возвратов отражать существующими Collections/Cleanup payout-журнала. До записи оплаченного rev2 под project lock требуются точные RemovedSaved + IssuedSaved и свежая проверка отсутствия строительных меток; подбор не является условием. Чтение журналов отменённого плана привязать к той же операции, исходной ревизии1, неизменным миру/чертежу/отпечаткам деталей и выдачи. Новая выдача после terminal запрещена; разрешено продолжение существующих collection/cleanup.

Сначала сделать явное взаимодействие с самим защищённым источником без OpenBoard и молотка: точный плательщик/мир/единственная метка/blob/дистанция/свободная ячейка. После сохранённого получения — автоматический cleanup и ограниченная сверка при старте. Native pickup/merge остаются закрытыми. Утраченные/откаченные журналы требуют сверки; rev2 сам по себе не означает полного расчёта. Согласованный откат всех файлов остаётся необнаружимым без внешнего монотонного якоря при обоих вариантах формата.

268 реализует только предпосылку — защиту неоплаченного повтора: исходная ревизия и отсутствие следов исполнения/удаления, включая повтор той же операции. 270 добавляет взаимодействие с источником и последующую очистку в коде/CPU-проверках, включая повторную проверку native-дистанции; это не приёмка E в игре. Полная оплаченная отмена, интерфейс, crash/rollback и нулевая стоимость открыты. См. [270](CHECKPOINT_270_RU.md).

В [289](CHECKPOINT_289_RU.md) добавлен `ProjectStore.CancelPaid`: под существующей блокировкой сначала сохраняется необязательная привязка к неизменной выдаче, затем прежний plan rev2. Старые rev1/rev2 и payout без привязки сохраняют прежние байты. Сбой второго commit оставляет frozen intent, повтор может завершить его; новая выдача запрещена, после закрытия получение/cleanup продолжаются. Поколения старых cleanup не переписываются; новые операции учитывают самый поздний известный world save. CPU172 проверяет эти границы. Native async caller со свежим construction absence/profile, повтор при загрузке, исчезновение таблички/призрака и полный игровой paid-cycle ещё не подключены. Это не готовая отмена через интерфейс и не доказательство защиты от согласованного отката всех файлов.
