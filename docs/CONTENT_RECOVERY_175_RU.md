# .175 — метка объекта и явный возврат после сверки

13 октября 2026. Реализована основа восстановления; наполненные хранилища в игровое размещение ещё не включены.

## Исправленная граница native identity

В проверенном Valheim Steam25730771 `ZDO.Save` не сохраняет сетевой UID и revision. `ZDO.Load` назначает новые UID и обнуляет revision. Поэтому старые `TargetUser/TargetId/Revision` журнала не доказывают тождество объекта после загрузки. В .173/.174 эти значения были пригодны для диагностики текущей сессии, но не для заявлений о восстановлении после перезапуска.

Native `Set(int,string)` сохраняет строку через `ZDOExtraData`, увеличивает revision и помечает sector dirty. Это подтверждено чтением текущих тел методов; не доказательство выполненного save. Подробный private-контракт и выбранные декомпиляции: `artifacts/checkpoint-0.19.175/native-persistence-contract.md`, `native/`. Игровые исходники не включаются в Git.

## Что делает код

- Journal v3 сохраняет прежний v2 layout, но требует сохраняемую метку `ostrix_buildworks_storage_transfer_v1` на target ZDO. Для forward метка — GUID операции; для return — GUID родителя. Новые объекты не получают старую сетевую идентичность.
- Сначала записывается и flush-ится Prepare. Только затем проверенный владелец ставит native-метку. Ошибка записи сохраняет журнал и удержание; содержимое ещё не перемещается.
- Метка меняет revision, поэтому native Container должен обновить cache. `MoveNext` возвращает `Ready` без Attempt/unequip/передачи, пока не синхронизируются cache и read-only capture. Ожидание ограничено30с монотонным таймером. После синхронизации есть отдельный `Ready` шаг, затем обычный mover.
- `InspectRecovery` ничего не меняет. `TryBeginRecoveredReturn` вызывается только явно: читает целый v3 forward с полностью наблюдаемым успешным префиксом, без InFlight/Uncertain/конфликтующего child. Это не автозапуск и не повтор прямой передачи.
- Требуются точная сохраняемая метка, текущий world/player/creator/prefab/grid, доступ/ownership, полные manifests обеих inventory, исходный raw `s_items`, свежий cache и точные предметы в записанных ячейках. Старый UID и старая revision не используются как разрешение. Каждый предмет должен подходить по prefab/quantity/текущим свойствам/maxStack/quest/equip; нужны отдельные пустые ячейки игрока.
- Привязываются свежие живые `ItemData`, затем используется общий обратный native mover .174. Предметы не создаются из архива, не ремонтируются, не сливаются и не выбрасываются. Подготовка перепроверяется до child Prepare.
- V1/v2 читаются и удерживаются, но не разрешают восстановление. При отсутствии надёжной метки legacy/unmarked операция консервативно удерживает контейнерные операции соответствующего мира. Метка без доступного журнала тоже запрещает удаление. После локального возврата оба журнала остаются unresolved, строительная цена не возвращается.
- Метка не входит в сохранённое содержимое чертежа и не переносится как идентичность новой постройки. Она не является административным разрешением или криптографическим подтверждением сервера.

## Что ещё не сделано

Нет успешного native save/reload в игре, disk readback, server ack, восстановления неопределённого/частично выполненного child, полного возврата строительной оплаты и Container placement. Callback `WorldSaveFinished`/`SavingFinished` не означает успешную запись; remote profile-save RPC не имеет ответа. Между profile клиента и world сервера нет общей native-транзакции. До отдельного протокола сохранения/серверной сверки hold не снимается.

Следующий шаг: подтверждения сохранения и серверная сверка состояния операции, затем подключение передачи после оплаты и полный изолированный игровой стенд. Постоянный проект/колышек/v11 остаются следующими зависимыми блоками. Нового ручного теста наполненного сундука пока нет; существующая ручная очередь импорта/auto-snap/редактора остаётся актуальной.
