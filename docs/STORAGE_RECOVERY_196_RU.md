# .196 — точная причина отказа восстановления сундука

Проверено 2026-10-16 на Valheim Build25909357. .196 улучшает диагностику;
восстановление наполненных хранилищ пока не исправлено и не включено для игроков.

## Что произошло в Valheim

Подготовленный полный сценарий .187 впервые выполнен на .195: один сундук,
оплата10 Wood, перенос2 собственных Wood, подтверждённое парное сохранение
персонажа и следующего поколения мира. Остаток игрока1 Wood. После штатного
logout/enter строгая сверка отказала; предметы, сундук и журнал сохранены.
Сценарий вызывает PlacePiece/ConsumeResources напрямую и не доказывает весь
пользовательский TryPlacePiece или обычное наполненное строительство.

.196 установлена через Deploy-TestBuild.ps1; SHA-256 DLL
66A3CDAEB19148B4C029C3D462B91C3E06310E5CB043DE4B9A74989367C8CD04.
131 защищённый файл при установке неизменен. Запуск через Thunderstore Modded,
только BW_QA_43d3719a. Повторной выдачи, строительства и переноса не было.
Read-only проверка прежней операции сообщила:

`Player inventory manifest changed.`

До этой причины прошли проверки идентичности операции/мира/игрока/сундука,
переданных предметов и их свойств, соответствия нативному содержимому,
количества записей и актуальности ревизии сундука. Последующие проверки
контейнерного manifest/hash после раннего отказа не выполнялись.
Служебный сценарий диагностики прошёл; сама recovery осталась отказавшей.

## Доказанная причина

Текущая ItemData.Save записывает `int(m_durability * 100f)` с усечением;
ItemData.Load восстанавливает `ReadInt() * 0.01f`. Это преобразование
не идемпотентно: повторная запись загруженного float иногда теряет ещё сотую.

Сохранённые read-only копии `.fch`/`.fch.old` разобраны с проверкой SHA-512
оболочек. У WAL проверена SHA-256 цепочка пяти кадров. Полный inventory hash
старой копии совпал с SavedPair.PlayerInventoryHash, а полный manifest — с
Observation.SourceManifest. В следующей копии отличается только прочность
молотка в ячейке(1,0):1887→1886. Остальные сериализованные поля и записи совпали.
Текущий live float18.85999870300293 точно равен `float(1886 * 0.01f)`;
следующая native Save записывает1885. Семь утверждений прошли.

Полный hash старого файла персонажа НЕ совпадает с SavedPair.ProfileHash:
штатный logout обновил другие секции. Это доказательство сохранённого
инвентаря, а не точного совпадения всего первоначального файла персонажа.
Независимый проверяющий подтвердил эту границу и механизм ошибки.

## Следующий шаг и открытые границы

Нужна версия журнала с ограниченным точным состоянием инвентаря в момент
подтверждённого парного сохранения и проверенной для текущего хоста проекцией
Save→Load. При recovery сравнивать загруженные поля напрямую; повторная
SnapshotItem сериализация прочности даёт ложное отличие. Остальные свойства,
ячейки, количества, происхождение и права остаются строгими. Это пока проект
исправления, а не реализованная поддержка.

Не принимать epsilon, диапазон или произвольную потерю прочности. Не патчить
глобальную сериализацию Valheim. Старый WAL остаётся удержанным; его нельзя
перезаписывать, удалять, повторять выдачу или автоматически компенсировать.
Дополнительные циклы сохранения требуют собственного доказательства, их нельзя
объявлять одним Save→Load. Далее нужны durable recovery/return/settlement,
обычная наполненная стройка, отмена/сбои, крепления/стойки и серверная проверка.
Цель ACTIVE; готовность всего модуля не заявляется.

После диагностики god/ghost выключены, выполнен штатный logout и выход из
Valheim. Отсутствие процесса проверено; собственный временный GABS остановлен
после сверки пути/PID/UTC-времени. Первый разбор времени cleanup получил

проверка с DateKind String завершила cleanup и подтвердила отсутствие helper.
