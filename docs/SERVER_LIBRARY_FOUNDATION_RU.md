## Граница полномочий

Core принимает **уже аутентифицированный principal**. Его нельзя читать из запроса. Resolver прав задаётся серверным адаптером; клиент не передаёт `isAdmin`. BlueprintServerAuthority связывает principal с текущим прямым соединением, проверяет серверный режим, готовность peer и совпадение socket, затем использует native `ZNet.IsAdmin`.

В текущей DLL Valheim `ZRoutedRpc.RPC_RoutedRPC` десериализует sender из payload, не использует входной ZRpc для его аутентификации. Поэтому routed sender UID не подходит для проверки административных прав. Native RPC_Kick/RPC_Ban используют socket.GetHostName → admin-list policy; это подтверждено чтением IL. Никаких игровых RPC этим этапом не регистрируется. Сам адаптер не является полноценным handshake/сетевым тестом.

Серверные файлы — отдельные `<id>.bwserver.zip`, ровно `access.json` и `blueprint.buildworks.json`; формат metadata version1, ID/revision/access/publisher/editor/time/SHA. Временные файлы не входят в каталог. Portable-документ остаётся существующего формата: стоимость, права строительства, административное восстановление и world/network identity не меняются.

Пределы:512 записей,128 МиБ суммарных stored и unpacked bytes,100000 деталей суммарно;32 МиБ portable-документ и4096 bytes metadata. Предел распаковки проверяется до чтения члена ZIP; физический файл ограничен уже на открытом FileStream. Повреждение записи останавливает загрузку целиком; частично загруженный публичный кеш не публикуется. Внешнее изменение проверяется перед чтением/заменой/удалением; автоматическое слежение за ручными правками файлов не реализовано.

## Следующий рабочий срез

1. Привязать хранилище к UID загруженного серверного мира; localhost разрешать отдельным проверенным решением локального host. Клиентская папка не становится серверной библиотекой.
2. Разделить тяжёлую подготовку/чтение и commit: worker получает чистые снимки, текущие native права проверяются на host-потоке перед публикацией. Нынешний синхронный core нельзя просто вызвать на worker с Unity-resolver.
3. Зарегистрировать прямые peer ZRpc callbacks, ограничить пакеты/чанки, частоту, общую память, timeout/cancel/replay; отписка и очистка при disconnect/world change.
4. Подключить одинаковый сценарий каталога редактора/молотка: источник «Сервер», просмотр доступного списка, принятие личной копии; admin publication/access/update/delete с явным результатом и причиной отказа.
5. Проверить настоящий host+remote, отзыв прав, переподключение и restart. Только после этого отмечать игровую серверную поддержку. Личная передача между игроками требует отдельного принятия и сохранения ограничений происхождения.
