# Быстрое управление Valheim: исследование 2026-10-12

Запрос Ostrix: найти инструменты для быстрого управления игрой, вместо ожидания
ответа модели после каждого движения. Исследование документации и исходников;
ничего не установлено, игра не запускалась, скорость на этом ПК не измерена.

| Инструмент | Подтверждено источником | Граница |
| --- | --- | --- |
| [NitroGen](https://github.com/MineDojo/NitroGen) | Модель видит изображение и выдаёт действия геймпада для Windows-игр | Видит последний кадр, авторы исключают длинное планирование и прохождение целиком. Работа в Valheim/BuildWorks не подтверждена |
| [Airtest](https://github.com/AirtestProject/Airtest) | Локальные сценарии проверки игрового интерфейса по изображениям; Windows поддерживается | Сценарии нужно написать; это не самостоятельный игрок |
| [DXcam](https://github.com/ra1nty/DXcam) | Непрерывный захват кадров Windows с буфером последних кадров | Ускоряет получение изображения, но не принятие решений моделью. Чужой FPS не является измерением нашего ПК |
| [PyDirectInput](https://github.com/learncodebygaming/pydirectinput) | Клавиши через scan codes/SendInput и относительное движение мыши | Только ввод; без распознавания сцены и планирования. Valheim не проверен |

Особенно важен [исходник среды NitroGen](https://raw.githubusercontent.com/MineDojo/NitroGen/main/nitrogen/game_env.py):
GamepadEnv создаёт xspeedhack.Client, perform_action вызывает unpause/pause,
которые выставляют скорость 1/0. В штатном варианте это вмешивается в ход времени;
он не подходит без изменения среды для доказательства обычной физики, стройки
и сетевого поведения BuildWorks. Частота выдачи действий не доказывает такую же
частоту независимых решений модели.

[Poco Unity SDK](https://github.com/AirtestProject/Poco-SDK/tree/master/Unity3D)
требует добавить файлы в Unity-проект и PocoManager.cs на GameObject. Готовая
совместимость с собранным Valheim через BepInEx не установлена. AltTester тоже
требует инструментирования игры; это не доказанный готовый переход.

Поиск доступных плагинов не дал подходящего игрового контроллера. Neuronto
вернул UE5-gameplay-mcp, LÖVE2D MCP и обычную автоматизацию рабочего стола;
готовая совместимость с Valheim не подтверждена. Заявления каталогов не
приняты за проверенную работоспособность.

## Рекомендация для BuildWorks

Сохранить существующий изолированный QA-канал и добавить локальное выполнение
ограниченного сценария с обратной связью: наблюдать состояние, выполнять ввод,
проверять условие, продолжать без обращения к модели после каждого шага.
Airtest подходит для изображений/проверок UI; DXcam и относительный SendInput
имеют смысл только при измеренном недостатке существующего захвата/ввода.
Новый сервер MCP мыши сам по себе не устранит ожидание между ответами модели.

В текущем BuildWorksQaControl ввод исполняется в процессе игры, но наблюдение
публикует снимок PNG и результат команды. Доля затрат ReadPixels/EncodePNG,
обмена файлами и ожидания модели пока не измерена; причина конкретной задержки
не объявляется установленной только по чтению кода.

Первый проверяемый опыт: один безопасный сценарий поворота камеры/выбора молотка
и UI в прежнем QA-мире. Измерить полное время и задержку наблюдения, подтвердить
остановку, освобождение клавиш, отсутствие действий при потере фокуса/смерти,
отсутствие изменения игрового времени. Затем использовать тот же исполнитель
для новой серии snap на .163. Строительство, стоимость и права остаются штатными.
Разработка исполнителя и установка зависимостей этим исследованием не выполнены.
